# Systematic Debugging

出典: obra/superpowers skills/systematic-debugging (MIT, commit 22f0b46) https://github.com/obra/superpowers
ライセンス全文は `references/upstream-LICENSE.txt`。骨格は upstream のまま、例と規約をこのリポジトリに合わせている。

## 核心

**原因を特定するまで修正しない。症状を直すのは失敗。**

## 鉄則

```
Phase 1 を終えるまで修正案を出さない
```

Phase 1（原因調査）が終わっていないなら、修正案を書いてはいけない。

## 使うとき

テスト失敗、golden の `changed` 増、実機の想定外挙動、ビルド失敗、settle の非収束、
RE の取り違え。**「たぶんこれが原因」「1 行で済む」と思ったときほど使う。**

## Phase 1: 原因調査

修正の前に必ず:

1. **エラーを最後まで読む**。`::error::` 行・exit code・行番号・ファイルパスを飛ばさない。
   スタックトレースは途中で読むのをやめない（誤診する）。
2. **再現させる**。再現しないなら推測せず証拠を増やす。
3. **直近の変更と環境差分を見る**。`git log -p -3` / `git diff` / PATH・
   `OBLIVION_RUST_HOST_TRIPLE`・adb の状態など。
4. **多層の不具合は境界ごとに実測する**。このプロジェクトでは
   **タップ → UI 値 → パネル状態 → `chargen_commit` → プレイヤー** のように区間を切り、
   1 回の実行で切れている区間を出す。掘るのはそこだけ。
5. **悪い値の発生源まで遡り、症状ではなく発生源で直す**。

## Phase 2: パターン照合

1. **動いている類似実装を探す**（例: Gender の参照実装）。
2. **参照は最後まで読む**。部分理解はバグを保証する。
3. **動く側と壊れる側の差分を、小さいものも落とさず列挙する**。
4. **依存を確認する**（設定、権限、環境、前提）。

## Phase 3: 仮説と最小検証

1. **仮説を 1 つ文章にする**（「X が原因だ。なぜなら Y」）。
2. **最小変更で試す**。同時に複数変えない。
3. 通らなければ**新しい仮説**を立てる。上に積み増さない。
4. 分からなければ「分からない」と書く。

## Phase 4: 実装

1. **失敗する再現を先に作る**（テスト、probe、1 回きりのスクリプトのいずれか）。
2. **原因への変更を 1 つだけ**入れる。ついでの改善は `.ai-todo` に起票して触らない。
3. **検証する**。golden が `changed=0` で維持されるか。陰性対照が落ちるか。
   実機ログに値が出るか。
4. 通らなければ Phase 1 に戻る。

## 3 回で設計を疑う

同じ症状に 3 回入れて駄目なら **4 回目を書かず設計を疑う**。
修正のたび別の場所に症状が出るなら構造が違う。verifier の 3 回 REJECT と同じ扱いで
人間に上げる。

## 赤信号（出たら STOP して Phase 1 に戻る）

- 「とりあえず直して後で調べる」
- 「たぶん X だから X を変える」
- 「複数まとめて変えて 1 回テスト」
- 「テストを飛ばして手で確認した気になる」
- 「原因を追わずに修正案を並べる」
- 「2 回失敗後の、もう 1 回だけ」

## 原因が無いと確定したとき

調査内容を書いてから、**リトライ・打ち切り・エラー表示**のいずれかで扱い、ログを足す。
ただし **「原因なし」の 95% は調査不足**。
