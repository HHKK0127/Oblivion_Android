🔴 重大な修正点
1. NIFブロックIDの誤り
現状の NIFBlockType（bhkCollisionObject = 0x0A0 など）は実際のNIFフォーマットと一致しません。OblivionのNIF（ver 20.0.0.4〜20.3.0.9）はブロックタイプを文字列（bhkCollisionObject）またはNiObjectタイプのハッシュで管理しますが、0x0A0といった連番は誤解を招きます。
// 正しいアプローチ: 文字列ベースまたはNiStreamのブロックタイプマップを使用enum class NIFBlockType : uint32_t {    // NIFファイルヘッダーのブロックタイプ文字列をハッシュ化    // または単純に文字列比較};
2. NiSkinDataの構造が不正確
現状の VertexWeight（固定4ボーン）はGPU転送用の構造であり、NIFファイル内の生データ構造とは異なります。OblivionのNiSkinDataは以下の構造です：
struct NiSkinData {    struct BoneData {        NIFTransform skinTransform;  // ボーンのバインドポーズ        std::vector<VertexWeight> vertexWeights; // 可変長（1頂点あたり1〜Nウェイト）    };    std::vector<BoneData> boneData;    // ...};
重要: NIFでは頂点ごとのボーン数が可変（1〜15程度）です。uint8_t boneIndices[4] はGPU用にパックする際の構造で、パーサー段階では可変長を保持すべきです。
3. NiSkinPartitionの欠落
Oblivionのスキニング実装では NiSkinPartition が必須です。これは頂点をボーン数ごとに分割し（1ボーン、2ボーン、4ボーンなど）、GPUでのスキニング効率を上げるためのデータです。これがないと実機（特にモバイル）でパフォーマンスが出ません。
struct NiSkinPartition {    struct Partition {        std::vector<uint16_t> bones;      // このパーティションで使用するボーン索引        std::vector<VertexWeight> weights; // パック済みウェイト        std::vector<uint16_t> indices;    // インデックス    };    std::vector<Partition> partitions;};
4. bhkCollisionObjectの構造が単純すぎる
実際のOblivion NIFでは：
bhkCollisionObject└── bhkRigidBody (Havok RigidBody)    ├── bhkRigidBodyCInfo (質量、摩擦、反発係数など)    └── bhkShape (形状階層)        ├── bhkBoxShape / bhkSphereShape / bhkCapsuleShape        ├── bhkConvexVerticesShape (ConvexHull)        ├── bhkMeshShape / bhkPackedNiTriStripsShape (TriMesh)        └── bhkMoppBvTreeShape (BVHラッパー)
現状の CollisionObject 構造では bhkRigidBodyの物理パラメータ（質量、摩擦、レイヤー情報、collision filter）が欠落しています。Oblivionの衝突フィルタ（bhkCollisionFilter）は非常に重要です。

🟡 設計改善の提案
5. Animation: NiControllerManagerの欠落
Oblivionのアニメーションは単なる NiKeyframeController の集合ではなく、NiControllerManager がトップレベルで管理します：
NiControllerManager├── NiControllerSequence (アニメーションクリップ)│   ├── NiTextKeyExtraData (イベント)│   └── Controlled Blocks (NiKeyframeControllerなど)└── NiDefaultAVObjectPalette
現状の設計では「クリップ」という概念が独自実装になりすぎており、NIFの NiControllerSequence と対応していません。
6. CollisionWorld: 空間分割の再考
グリッドベースの空間分割（CELL_SIZE = 64.0f）はOblivionの広大なワールド（1セル = 4096単位）では非効率です。以下のいずれかを推奨：
AABBツリー（Dynamic AABB Tree）: 静的・動的オブジェクト両方に対応
Sweep & Prune: 移動体が少ない場合に有効
または、単純なBVH + ブロードフェーズ/ナローフェーズの分離を明確にする
// 推奨: ブロードフェーズとナローフェーズを分離class CollisionWorld {    // ブロードフェーズ    std::unique_ptr<BroadPhase> broadPhase; // AABB Tree or Grid        // ナローフェーズ    static bool narrowPhaseTest(const CollisionShape& a, const CollisionShape& b, ...);};
7. スキニングシェーダーのUBO制限
uniform mat4 uBoneMatrices[MAX_BONES]（MAX_BONES=128）はOpenGL ES 3.0のuniform配列制限に依存します。安全のため：
// UBOを使用する場合layout(std140) uniform BoneMatrices {    mat4 bones[128];  // UBOのサイズ制限に注意（ES 3.0最小: 16KB）};
または、テクスチャベースのボーンマトリクス（ボーンテクスチャ）を検討するとより安全です。

4. もう一つ、設計上の重要な提案
CollisionWorldは「Physics Engine」ではなく「Collision Query Engine」として設計してください。
現状のHavok再現率30%ですが、Oblivionで本当に必要なのは「Havokの物理シミュレーション（剛体落下、布、ラグドール）」ではなく、「Havokの衝突判定（レイキャスト、スイープ、オーバーラップ）」です。
// こうするべきではない：class PhysicsEngine {  // 力積分、ジョイント解決、睡眠判定...    void stepSimulation(float dt);};// こうする：class CollisionWorld {  // クエリ専用。軽量。    bool raycast(...);    bool sweepSphere(...);    bool checkOverlap(...);};
これにより： - 実装工数が1/5に削減できる - モバイルのバッテリー消費を抑えられる - 必要になった時点で、後からBulletやJolt Physicsなどの本格物理エンジンを後ろに被せられる
