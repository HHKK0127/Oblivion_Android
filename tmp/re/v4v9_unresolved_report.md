**vtable 照合できた具体例（別セッションの V3 由来・生バイト検証済み）**:
`0x4AE990` は `mov edx,[ecx]` → `mov eax,[edx+0x354]` → `call eax`。
オフセット `0x354` = スロット `0xD5` (213) で、RTTI vtable の大規模クラス
（n_methods > 214）のみが候補となる vt+0x354 呼出として文書と一致。

#### K4 その他 — call を1つも持たない完全インライン処理（11件）

> **⚠️ 訂正（2026-10-23, V17）**: 下表の ScriptEffect 4件（`0x0011`/`0x0012`/`0x0013`/`0x10BA`）の記述
> 「`fldz` + null チェック → 0.0 返却」は**不完全で、no-op でもない**。実際は:
> `fldz` で結果スロットに **0.0 既定**を `fstp [ecx]` で書いた後、**状態バイトを判定**
> （Start=`byte0` / Finish=`byte1` / Update=`obj+0x29`）し、**成立時は `fld1`（1.0）で上書き**する。
> `Elapsed` は `[eax+4]` の実経過秒。**戻り値は全件 `mov al,1`**。call が0件なのは完全インライン実装のためであり、
> 「引数を読んで何もしない」状態ではない。**移植で no-op 化は不可。**
> また ディスパッチャは **`0x5169A0`（イベント系）/ `0x4FCA30` GetOpcodeEntry 経由（汎用系）/ `0x4FAB20`（カーソル系）**
> の3経路、+0x1C は既定 `0x4FDE30`・+0x20 は0（代替経路なし）。
> 詳細: `tmp\re\v17_scripteffect_noop_report.md`（417行）。下表の残り7件（Toggle 系/Get系）も V17 で全件**実処理**と確認済み（no-op 0件）。

| # | 事実 | エビデンス |

| 3 | その窓の頭5 call = `0x24CD198D, 0x4D8A30, 0x9832E6, 0x65A2C0, 0x88D370` | `0x509030` から線形デコード（先頭命令が `call 0x24cd198d`） |
| 4 | `.bak` の旧セル = ③の各値 **−0x400**（`rawptr 0x800` バグ） | `0x24CD198D−0x400=0x24CD158D` ✓ / `0x4D8A30−0x400=0x4D8630` ✓ / `0x9832E6−0x400=0x982EE6` ✓ / `0x65A2C0−0x400=0x659EC0` ✓ / `0x88D370−0x400=0x88CF70` ✓（**5/5 完全一致**） |

**結論**: `0x24cd158d` は「窓先頭 `impl+0x400` の境界ずれデコード値 `0x24CD198D`」に
「0x400-low マッピングバグ」が重なった2層ノイズ。TODO_re49 の仮説
（窓先頭 0x509030 / `E8 58 89 7C 24`）は**窓とバイト列まで正確に一致**し、
記録値のみ −0x400 ずれていた（＝仮説は実質的に正しい）。
**この1行が3つの補正キャンペーンを全て生き残った唯一の残存ノイズ**。
