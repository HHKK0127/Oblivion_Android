## §1 項目1（R-1）: `NiTMapBase` slot5/slot6 の純粋仮想2本の意味名

**判定: 【解明】slot5 = 「マップノード割当フック（AllocateNode）」、slot6 = 「マップノード回収フック（DeallocateNode）」。
NiTMapBase の汎用コードが新規挿入時にノード（12B = `{next, key, data}`）を作る口（slot5）と、
削除／デストラクタ走査でノードを返す口（slot6）が純粋仮想化されており、具象側の 0x4F0F60/0x4B2ED0 は
エンジン共通の **12B ノードプール**（グローバルフリーリスト `[0xB33EAC]`、CS `0xB33F00`、
一括補充 2048 ノード = `new(0xC*0x800)`）への pop / push として実装されている。
呼び出し文脈（Insert ＝ slot5、map dtor ＝ slot6）から機能名確定。RTTI 上的な関数名は非掲載なので機能名で裁定。**
（なお名は本分析による機能名であって、エンジン原典のシンボル名ではない点に留意。）

### §1-1 汎用コードからの呼び出し実測（`v253_scan1` A）

- **Insert `FUN_00452710`**（`thiscall(this, key, value)`、`ret 8`）:
  1. slot1 hash（`call [vtable+4]`）→ slot2 keyeq でチェーン走査（`0x452730..0x452747`）。
  2. 未登録時 **`0x45274B: mov edx,[eax+0x14]` → `0x452750: call edx` ＝ slot5 呼び**（引数ゼロ、ecx=this）。
     返値 edi = 新規ノード。
  3. **`0x45275B: mov edx,[eax+0xC]` → push 値／ノード／キー → `call edx` ＝ slot3 setter**（`ret 0xC`）で
     `node+4=key, node+8=data` を書かせ、`[node]=旧バケット頭; bucket[hash]=node; [this+0xC]++`（要素数）。
- **map dtor `FUN_007C2A40`**（vtable_B slot0 の 0x584470 が呼ぶ汎用クリア）:
  バケット全走査で各ノードに対し **`0x7C2A6F: call [eax+0x10]`＝slot4 cleanup（POD では `ret 4` の no-op）** の後、
  **`0x7C2A79: mov edx,[eax+0x18]` → `0x7C2A7F: call edx` ＝ slot6 呼び**（push ノード）。最後に `[this+0xC]=0`。
- Find `FUN_004527A0` は slot1/slot2 のみ（割当不要）＝ slot5/6 に触れない — 役割の非対称性も一致。

### §1-2 具象 thunk とプール実体の対応（`v253_scan1` B、`v253_scan2` C/E）

- slot5 thunk `0x4F0F60`: `add ecx,0xC; jmp 0x44D810`（int3 パディング付きのコンパイラ生成 thunk）。
- slot6 thunk `0x4B2ED0`: `mov eax,[esp+4]; mov dword[eax+8],0; mov [esp+4],eax; add ecx,0xC; jmp 0x44D880`
  — **ノードの data（+8）をゼロクリアしてから回収**する前処理付き。
- プール割当 `0x44D810`: `EnterCriticalSection(0xB33F00)` → `GetCurrentThreadId()` を `[0xB33F78]`、再入計数を
  `[0xB33F7C]` に記録 → フリーリスト頭 `esi=[0xB33EAC]`。空なら **補充 `0x44D770`**（`[0xB0686C]=0x800`=2048 ノード
  × 12B を 1 ブロック `new(0x6000)` で確保し 12B 刻みで next を直結、旧ブロック群は `[0xB33EA8]` 連鎖で保持。
  ブロック自体は解放されず arena 式）→ 頭を pop し **`*node=node[1]=node[2]=0`（12B ゼロクリア）で返す**。
- プール回収 `0x44D880`: 引数ノードの `node[1]=0; node[0]=旧頭; [0xB33EAC]=node` ＝ **先頭へ push**。
- 両関数とも**調整後の ecx（this+0xC）は一切読まない**（グローバルプールのみ使用）。`add ecx,0xC` は
  テンプレート由来の習慣的 this 調整で動作上 inert（NiTMapBase の +0xC は要素数フィールドであり、
  カウントとの重なりは意味を持たない）。
- プールの直接共有者（E8 走査で各 1 箇所）: `0x7ABDED`（ intrusive な 12B ノード生成側）と
  `0x7C31C7`（`lea ecx,[ebx+0xC]` で同プール回収を直呼び）— 他コンテナも同一 12B ノードプールを使う
  エンジン共通機構であることを裏付け。

### §1-3 共有範囲＝テンプレート一群の証左（`v253_scan2` D）

- .rdata 全体で dword `0x4F0F60` を含むスロットは **176 箇所**、`0x4B2ED0` は **132 箇所**
  （例 `0xA3840C/0xA38D20/0xA3A280../0xA3AAAC/0xA3BDEC..`）。つまり **NiTMapBase 系 vtable の大半が同一の
  ノード割当／回収 thunk を slot5/6 に持つ** — 「純粋仮想2本＝ノードアロケータフック」の解釈が
  キー型（u8 / char const*）・値型を問わず一貫する。
- 抽象側（`0xA3904C`/`0xA69688`/`0xA696A8`）の slot5/6 が `_purecall` を置換できないことと、
  具象側（`0xA3AA98` を含む 176 系）が必ずこのペアを持つことは表裏一体。v250 §4 の「呼べば R6025 で abort」は
  **Insert/dtor が実際にこの2本を呼ぶ**ことを示す本節で補強完了（基底名義の静的オブジェクト 0xB13948/0xB1395C が
  Insert/dtor されれば abort する構造だった、とも説明がつく）。
- 7 スロットの意味名（機能名・裁定）: `[0]` dtor / `[1]` hash（**ポインタ値そのものの mod**。char* 版 0x6A9060 も
  文字列比較でなくポインタ同一の keyeq 0x763E80 と対になっており、キーは文字列内容ではなくポインタ値で管理）/
  `[2]` keyeq / `[3]` set_key_data / `[4]` cleanup_node（POD no-op）/ `[5]` **allocate_node** / `[6]` **deallocate_node**。

### §1-4 [PORT] 含意

- 移植側は slot5/6 を「ノードプール割当／回収」のフック 2 本として実装すれば意味が閉じる（NiTMapBase の
  Insert/erase/dtor がノード生命周期でこの2本を呼ぶ設計自体は保持）。エンジン共通 12B プールの
  CriticalSection／arena 補充は移植不要で、普通の `new/delete` をフック内に置いても外部挙動は同等
  （retail でこの2スロットが purecall のまま呼ばれた経路は無い）。
- R-1 は**消滅**。新規残点なし（この項目からは発生しない）。

## §2 項目2（R-2）: TileMenu 登録時の「ID しきい補正」の実体

**判定: 【解明（名称の実体はデータファイル側のみ残る）】qword `0xA69768`/`0xA69778` は double の **103.0 / 102.0**
（実測）であり、`0xFA5(4005)`/`0xFAB(4011)` は「代替 ID」ではなく **TileMenu+0x18 の設定パラメータツリーの u16 キー
（menu.xml 系 float パラメータ番号）**。登録関数 `FUN_00591C50` の末尾で
(1) `FUN_00588BD0(this, 4005)` が読んだ **パラメータ 4005 の float 値**を 102.0→103.0 の順に fcomp し、
**値 ≤ 103.0 のときだけ** ②内部メニューの slot13（ID）を `[inner+0x14]` へミラーし、③`FUN_00584980` が算出した
**レイアウト float（UI コンテナ窓 ID 1024 の子範囲 max、下限 10.0、+100.0 の余白）を `FUN_0058CEB0(4011, value)`
でパラメータ 4011 に保存**する。値 > 103.0（または NaN 系）なら ②③をスキップ。
**登録インデックス `ebx−999` と格納値（TileMenu this）はこのゲートの内外で一切変化しない** —
v250 §1-3 の「ID を 0xFA5/0xFAB 系の代替 ID へ補正」は誤りで、**「しきいゲート付きのパラメータ 4011 書込」**
が正しい（v250 自身の残点 R-2 解消を兼ねる訂正）。**

### §2-1 実測値・機構（`v253_scan3` A/B/C、`v253_scan4` A/B/C）

- qword 実測: `[0xA69768] = 103.0d`、`[0xA69778] = 102.0d`。近傍に float `6006.0f@0xA69770` / `6007.0f@0xA69764`
  （`FUN_00584880` の拡張版ゲートが同一パラメータ 4005 を 102/6006/103/6007 の順で比較するのに使用）。
  直前 0xA69758 は文字列 `'menu.xml'`（0xA69748 `'harGen\race_sex_menu.xml'` の末尾部分）— **この定数群は
  menu.xml 系 UI パラメータ機構の定数プール**である位置的裏付け。
- ゲッター `FUN_00588BD0(code)`（ecx=this）: `[this+0x18]` を根とする探索木を歩き、ノード `entry+0x18`（u16 code）で
  一致判定、見つかれば `fld dword[entry+4]`（float 値）、無ければ `fldz`（既定 0.0）。
- 探索/生成 `FUN_0058B220(code)`（呼出し 19 箇所・0x58C2xx〜0x58E7xx のパラメータアクセサ帯に集中）:
  無ければ `new(0x1C)` エントリを木へ挿入。**エントリ = 28B = {+0 子ポインタ, +4 float 値, +8 名前行,
  +0x18 u16 code, +0x1A dirty byte}**。
- セッター経路 `FUN_0058CEB0(code, float)`: `FUN_0058B220(code)` → エントリ存在時 `FUN_0058CA00(entry, value)`
  （値書込 + dirty 化 + code≠0xFDE のとき変更通知 `0x588930`/再適用 `0x58BEE0`。code 0xFDE=4062 は例外扱い）。
- `FUN_00591C50` の分岐（`v253_scan3` A 全文字）:
  - `0x591CB6..CC5`: `push 0xfa5; call 0x588bd0; fcomp qword[0xa69778]; test ah,0x44; jnp → 0x591CEB`
    — **val ≤ 102.0**（C3,C2 の片側だけ立つ＝小なり/等号）で書込経路へ。
  - `0x591CD2..CE9`: 再取得し `fcomp qword[0xa69768]; jp → 0x591D0F` — **val > 103.0/NaN** で書込スキップ、
    それ以外（102<val≤103）は書込経路。**帰結: 書込は val ≤ 103.0 と同値**。
  - 書込経路 `0x591CEB..`: `[edi+0x20]=ID` の後に続き **`mov [edi+0x14],eax`**（ID ミラー）→
    `call 0x584980` → `push 0xfab; call 0x58ceb0`（パラメータ 4011 へ float 保存）→ 0x591D0F の通常登録へ合流。
  - 合流後 `0x591D0F..`: `SetAt(ebx−0x3E9, &esi)` ＝ v250 §1 の登録本体（**ebx はゲートで変化しない**）。
- `FUN_00584980`（レイアウト float 算出、`v253_scan4` D / `v253_scan5` B）: `0x582160(0,1)` の UI ルート子列表を
  walk し、スロット 13 の ID が **0x400(1024)** の窓の子範囲を max 採集 → 末尾 `call 0x9828C0`（float→int）→
  **`fcom double[0xA3F3E8]=10.0` で下限クランプ（未満なら float `[0xA31C80]=10.0f` へ差替え）→
  `fadd double[0xA309F0]=100.0`** ＝ 「コンテンツ max 範囲(下限10) + 余白100」の px 値。
  → パラメータ 4011 に書かれる値は **パネル高さ様レイアウト寸法**と機能裁定。

### §2-2 業務的意味（裁定）

- **[確定]** 0xFA5/0xFAB はメニュー ID 空間（999..1049）や type code（4001..4014 の `push 0xfa2` 引数）とは別系列の
  **UI 設定パラメータ番号**で、retail 全体で `FUN_00588BD0` 98 箇所 / `FUN_0058CEB0` 1767 箇所の読取／書込が
  集中する「パラメータ accessor 機構」の一部。type 4002 の TileMenu 登録時にだけ、パラメータ 4005（バインディング
  値と見てよい数値）が 103.0 以下なら「窓 1024 のレイアウト寸法を参数 4011 へ伝搬＋ID ミラー」を行う。
- **[推定]** 業務的役割は **ロード/セーブ系メニューのパネル寸法・表示位置の自動補正**（QA や MOD で無効化
  できるしきい 102/103 付きのレイアウト propagation）。保存データの意味論（スロット番号・ファイル内容）には
  **一切影響しない** — 登録 index・格納 this は不変のため、v248/v250 のセーブスロット結論を揺るがすものではない。
- **[未確定]** パラメータ 4005/4011/4061/4062 の**名称**は EXE 内に存在せず、ディスク側の menu.xml 系 XML
  （`Menus\...\menu.xml`, `CharGen\race_sex_menu.xml` — 0xA69740 帯の文字列が同機構の存在を裏付け）に依存。
  名称特定はデータファイル解析の範疇として R-2b 新残点に落とす（低・移植不要）。
- 補足（副次観測・[確定]）: 2 つ目の `push 0xfa2` 呼出点 0x58A9A6 は TileMenu ctor 系の **メニュー項目テーブル
  登録関数**（`push 0xA6A5EC 文字列; push 0x7D6(2006) → call 0x58A0A0` を多数並べた後）で、項目 ID 群（2006/2027/3002..）
  の登録後に type 4002 設定を slot5 経路で適用している。0x42703E の `0xFA2` 出现は `jmp 0x427FE4` の相対オフセット
  （`E9 A2 0F 00 00`）の誤検出であり、push 形の 0xFA2 使用箇所は **2 箇所のみ**（0x58A9A6 / 0x591C54 の cmp）。
- [PORT]: 移植では「type 4002 登録後に `param4005 ≤ 103.0` なら `param4011 ← max(窓1024 子範囲,10)+100` を書く
  **UI レイアウト後処理 1 本**」として実装または省略可（省略時は寸法補正が起きないだけでスロット動作は同一）。
  現物互換を取るならしきい定数（102.0/103.0）と 4011 の意味（+100 余白の px 高さ）だけ保持すること。

## §3 項目3（R-3）: parser が optional Integer を書き込む out スロットの実位置

**判定: 【解明（＋不変条件の微修正あり）】out スロットは専用バッファではなく、ハンドラのローカル dword そのもの。
save ハンドラ `FUN_005023D0` では `esp0−0x310`（`sub esp,0x310` 直後のフレーム先頭スロット、＝ 0x5024A4 の
`cmp dword[esp+0x10],0` の対象）、load ハンドラ `FUN_00502500` では `esp0−0x30C`（0x5025D4 の `cmp [esp+0x14],0` の対象）。
パーサ `FUN_004FAE80` の out ポインタ配列は「引数スロット自身」で、ベースは先頭命令群の実測
`0x4FAEA8: lea esi,[esp+0x48]` ＝ **エントリ SP+0x20（＝ param_8 スロット）**。`&stack0x00000020`（decompiled :194611）の
実体確認。パラメータ1個消費ごとに +4 進むので、2 番目の引数（optional Integer）は
**param_9 スロットの値（＝ハンドラが push した dword のアドレス）が指す先**に書かれる —
save は &esp0−0x310、load は &esp0−0x30C を push している（§3-1）。
さらに本項目の副産物として、**その dword は読まれている**：まさに同じスロットが `cmp→setne` で
`FUN_00465130` の param_4（詳細診断表ゲート）になる。よって「第2引数は inert」は
**「値の大きさは捨てられるが、非ゼロ性だけ消費される」に厳密化**（`save foo` だけなら param_4=0、
`save foo 5` で 1、`save foo 0` は 0）。**

### §3-1 save ハンドラ側の四点同期（`v250_scan8` P1 の実文字列、アドレスは本節で機械検証）

`sub esp,0x310` 後、プロローグ push 4 個で esp_B = esp0−0x320。以降の参照はすべて同一スロットを向く:
1. `0x50241D: lea ebp,[esp_B+0x10]` → **ebp = esp0−0x310**、`0x502421: push ebp` ＝ 第9引数（param_9）。
2. `0x502435: mov dword[esp_E+0x34],0`（9 push 後 esp_E=esp0−0x334）→ **esp0−0x310 をゼロクリア**。
3. パーサ: 1 個目 String → `*(&param_8スロット)`＝esp0−…+0x10C の 288B 文字列バッファへ memcpy
   （`0x502422: lea ebp,[esp+0x120]` の push が param_8）。2 個目 Integer → `*(u32*)*puVar12`（:194641）で
   **`*(&param_9スロット)` = esp0−0x310 の dword に float→int 値**（`0x9828C0` 経由）。
4. `0x5024A4: cmp dword[esp_B+0x10],0 / 0x5024AD: setne cl` → 同一スロット（esp0−0x310）を param_4 として消費。
- ループ回数はストリーム内 u16 トークン数（`local_18+1 < local_c`、decompiled :194849-194852、
  `movzx edx,word[cursor+base]` は 0x4FAE90..0x4FAEA4 で実測）。**トークン 1 個（`save foo`）なら
  Integer 分岐自体が実行されず、スロットはゼロクリアされたまま → param_4=0**。

### §3-2 load ハンドラ側（`FUN_00502500`、v250 §3-3 の「同一構造」を位置まで特定）

- `0x50254D: lea ebx,[esp+0x14]`（= esp0−0x30C）→ `0x502551: push ebx`（param_9）。
- `0x502565: mov dword[esp+0x38],0` → 同一スロットをゼロクリア。`call 0x4fae80`。
- `0x5025D4: cmp dword[esp+0x14],0` → 同一スロット。save と違うのはスロット位置が +4 スライドした点のみ
  （esp0−0x30C。esp0−0x310 側には 0x502549 でディスパッチャ引数の写しが置かれ、こちらは parse 配列と無関係）。

### §3-3 裁定と v250/v248 への含意

- **位置（本題）**: [確定] 上記の 2 アドレス。所有は「ハンドラのローカルフレーム」で、ディスパッチャ由来の
  バッファ群（288B 名前一線）とは別。`&stack0x00000020` の意味論的実体（＝push 引数スロット列を配列として
  歩かせる設計）も [確定]。
- **消費の厳密化（不変条件との緊張点）**: タスク前提の「handler 未読」は *値の識別*（5 と 7 の区別）に
  ついては真だが、*非ゼロ性* は param_4 ゲートとして読まれる。v250 §3-3「整数用のスロットは読まれない」
  ／§2-1「console save param_4=1（通常）」／v248 §3-4「正常に引数が 1 個解釈されれば 1」は、
