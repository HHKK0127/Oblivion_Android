## §3 各残点の裁定

### 3-1 [V143] C 群 8 件の呼出し元復元 — **復元完了（18/18 site）**

- 手法: `.text` 全域 E8 スキャン（`0x401000` 起点 / 6,450,233 B）で 8 ターゲットの site を全数抽出 → site から遡って 2,048 B 以内の候補境界（padCC/00/90 ラン直後・terminator 直後・台帳開始点）を線形デコードし、**site に完全着地する最初（最短距離）の入口**を採用。
- 結果: **18/18 site で caller 入口を復元**（距離 4–7 B、着地 2 命令、直前 byte はすべて `CC`）。
  - site=0x410E25 → 入口 **0x410E20**（宿主 gap `[0x410C40, 0x410EB0)`）
  - site=0x9B91F7 / 0x9B9144 → **0x9B91F0 / 0x9B9140**、0x9D5Dxx–0x9D7Bxx の 15 site → **0x9D5D80 … 0x9D7BF0**（すべて gap `[D3DXVec4Transform=0x9A9D44, 次台帳 0x9D8020)`、幅約 190 KB = v127/v156 の巨大 tail 領域）
- 復元した caller 本体（証跡 `%TEMP%\opencode\v152_p1b_out.txt`）: `mov eax,[ebp-0x10] ; push eax ; call <target> ; pop ecx ; ret` 型の **4–6 命令ミニ wrapper**（先頭以外は `ret` で完結）。ラベル（台帳）は**全員 NONE** = 未登録。
- 重要な裏取り: 台帳関数の線形デコードから site へは**到達しない**（宿主 FUN_009A9D44 は入口から 1 命令で `int3@0x9A9D4A` 停止 / FUN_00410c40 は `int3@0x410D01` 停止）→ v140 の「site = unreached / 宿主線形 decode 不通」判定を**独立に支持**。
- wrapper 自体の呼出し元: E8/E9 サイト **0 件**、代わりに **imm32 参照**が存在（例 0x9B91F0→`.rdata 0xAE35C8`、0x9D5D80→`0xAFDD90`、0x9D6800→`.text 0x416D46`+`.rdata 0xAFE5E0`）= **関数ポインタ表（コールバック）経由の登録先**と同定。
- 裁定: C 群 8 件の呼出し元は「padCC 境界で独立化できる未ラベル wrapper 群（18 個）」に復元済。ただし wrapper 経由の上流（誰が 0x9D5D80 等を呼ぶか）は **imm32 テーブル参照の特定まで**で、テーブル走査側（登録コード）は別タスク（V145 のパイプラインと同型）= **残りは残点として起票（R-a）**。

### 3-3 [V145] P3 残余 call-origin（未知 22）— **初版裁定を撤回し、修正版で消化**

> **重大訂正（2026-10-28 追記）**: 本節の初版は「222 件を v140 と 100% 再現し、未知 22 件を 302 の FF15 site に 22/22 帰属させた」と裁定した。
> その**帰属計算そのものが誤り**であることを独立検証で特定した。原因は `read_ptr()` の実装バグで、
> **v140 の原本（`v140f2_cascade.py` L121–125）にも同じバグが存在する**（= 数値が一致したのは「同じバグを再現した」ため）。
> 下記 (a)–(e) の順に、再現 → バグ特定 → 修正版 → 正体 → 裁定を示す。

#### (a) バグ込み再現（v140 と同一実装であることの確認）

- 手法: `v140f2_cascade.py` の origin 付き CFG walk を独立再実装（F1/F2 を先に適用し accept を後段へ移す同一述語構成）。P0 → F1 → F2 → accept の順序は述語独立のため結果不変（検算で確認）。
- 再現結果（`%TEMP%\opencode\v152_p2_out.txt`）: P3 = **58,935**（期待 58,935）/ 未ラベル **40,724** / origin mix **unreached 40,502 + call 222** / 内訳 **known 147 / Cat-3 53 / unknown 22**（帯 `009E27B0..009E4200`）→ **v140 の全数値を 100% 再現**（＝v140 と同一実装。ここまでは正しい）。

#### (b) バグの特定 — `read_ptr()` の VA→file offset 変換

- 誤実装（v140 L121–125 / v152 L100–104 とも同一）: `read_ptr(va) = raw[va - ImageBase]`、すなわち **file offset を `va - 0x400000`** と仮定。
- 正: file offset = `va - section_const`。実測のセクション定数（`v162_verify.py` / probe12）:

  | セクション | VA | const (= VA − PointerToRawData) | 誤読のズレ |
  |---|---|---|---|
  | `.text` | 0x401000 | **0x400C00** | +0xC00 |
  | `.rdata` | 0xA28000 | **0x400E00** | **+0xE00** |
  | `.data` | 0xB02000 | **0x401400** | +0x1400 |

- 決定的な実測（`v162_probe10.py`）:

  ```
  0x448E39: call dword ptr [0xa28090]   -> 正しい値 [0xA28090] = 0x700A9A
                                            誤読     [va-0x400000] = 0x9E27F0
  0x44FA7E: call dword ptr [0xa28168]   -> 正 0x700E6E / 誤 0x9E3460
  0x403E33: call dword ptr [0xa282b0]   -> 正 0x700F06 / 誤 0x9E48D0
  ```

- つまり **「0xA2808C = 0x9E27D0」「0xA28088–0xA28258 が 0x9E27xx 帯の表」という初版の記述は誤り**。実際の `[0xA28088] = 0x700A6E`、`[0xA2808C] = 0x700A84`（`.text` の補助/thunk 帯）。0x9E27B0/0x9E27D0 が載っているのは **0xA28E88 / 0xA28E8C**（+0xE00 先）である。
- 初版が挙げた「302 site」は `call dword ptr [0xA28088/0xA2808C/…]` の site であり、**それらの実呼び出し先は 0x700A6E 帯であって 0x9E27xx 帯ではない**。

### 3-4 [V146] terminator の FF E0-E7 欠落修正 — **設計確定・判定結果は不変（検証済）**

修正規則（`%TEMP%\opencode\v152_p4_term.py` の `term_new()`）:

1. **誤認の遮断**: `data[e-2] ∈ {EB, E0..E7, CF, F4}` による 2 B terminator 判定のうち、`data[e-3] == 0xFF` かつ `data[e-2]` が modrm `0xE0..0xE7`（mod=11, reg=/4 = jmp r32）のときは**拒否**（その E0 は `FF E0` の第 2 バイト）。
2. **正規検出の追加**: `data[e-2] == 0xFF` かつ `data[e-1] ∈ 0xE0..0xE7`（同 modrm 条件）なら **`FF E0-E7` = jmp reg を 2 B terminator として受理**。
3. **`FF D0-D7`（call reg）は terminator にしない**（call は fall-through 継続）。`.text` 内に **29,830 箇所**あり、旧・新どちらのルールでも受理しないことを明記。
4. 既存の他パターン（`ret`/`ret imm16`/`E9`/`FF 25`/`0F 0B`）は不変。

## §7 Android 移植への示唆

移植側では「ラベル無し = 未実装」ではなく **(a) 実在証明済みの未ラベル wrapper（C 群 18 個・`mov/push/call/pop/ret` 型）→ 先にスタブ化、(b) ラベル済み台帳から呼出される未登録実体（保留 6 件）→ 統合表への追記候補（V159 L7）を優先して実体を移植、(c) CRT 初期化ループ 0x981CCB が `.rdata 0xA283D4–0xA2F77C`（7,402 エントリの `.CRT$XCU`）から `call eax` で起動する動的初期化関数群（0x9E27xx 帯を含む未ラベル領域）→ **移植時はこれらを「初期化フック」として一括登録し、`unimplemented(name, va)` ログは表エントリ単位で落とす**（従来の「FF15 表経由」という想定は §3-3 訂正により誤り）、(d) IAT スロット 0xA28090/0xA28168/0xA282B0 の未知 3 件 → 未登録のままなので先に名前付きスタブ化、の 4 層で未実装ログを分類できる。terminator の FF E0-E7 修正は境界生成ツール側の話で移植コードには影響しないが、**移植リポジトリでエントリ境界を再生成するツールを書く場合は本修正（§3-4）を最初から取り込む**こと（候補差 0.12%、ground truth 不変）。**ポインタ解決を再実装するツール（テーブル走査・間接 call 解決）では VA→file offset を必ずセクション定数（`.rdata` const = 0x400E00 等）で行い、`va − ImageBase` は使わないこと**（§3-3 の +0xE00 ズレ）。MinHash の near-dup クラスタ（1,386 / 8,778 成員）は「同じ実装を別名で数回移植する」事故の予防に使える——特に gap⇔gap外 13 クラスタ・4,347 ペアは Ghidra 未登録と登録済みで同一実装が並ぶ箇所であり、stub 実装レビューで二重実装しやすい地点を指す。本文なし 8 件（Cat-3b）は**デコンパイル本文すら無い**ため移植時の参照元は `v155_label_ledger_union.csv` の `Cat3b` 列をマーカーにする（実装は行わない）。
