### 2.2 ヒューリスティックの改良（重要な学習）

| 段階 | 規則 | 結果 | 判定 |
|------|------|------|------|
| 初版 | `e8(a)==0 ∧ e8(a+0x400)≥3 ∧ cc(a+0x400)` | 49 LOW / 8,878 AMBIG | **失敗**（大量のノイズ） |
| 最終 | 参照をセクション分割: `.rdata`/`.data` 参照のみ決定的、`.text` 内 imm32 は雑音とみなす | OK=2,169 / AMBIG=3,389 / **LOW=20** | 採用 |

**最終規則（S1）**:
```
rref(a)==0 ∧ rref(a+0x400)≥1 ∧ e8(a)==0 ∧ is_funcstart(a+0x400)
  → LOW（a が 0x400-low で、正しくは a+0x400）
```
`rref` = セクション別 imm32 参照数。`.rdata`/`.data` からの参照は
vtable・ディスパッチ表等の決定的証拠、`.text` 内の参照は誤デコード由来の雑音が多いため分離した。

**なぜ初版が失敗したか**: 実在関数でも直接 E8 呼出が 0 件のものが多数
（仮想関数・シンコール・スタブ）。`e8(a)==0` は「存在しない」指標にならない。

- **3 件は自前の訂正文書内**（`0x401B00` / `0x401B20` 等の旧値を「旧＝誤り」と記した箇所）→ 意図的、対象外
- **17 件が実検証対象** → 下記のとおり全件が誤検出

## 3. LOW=20 の全検証（17件すべて誤検出）

### 3.1 呼出元/オペランド文脈の誤読（5件）

| 候補 | 見た目 | 生バイトでの実態 | 判定 |
|------|--------|------------------|------|
| `0x597540` | e8(a)=0, a+0x400 が関数先頭 | `0x57AA7C` に **`jmp 0x597540`** が実在 → a は**ジャンプ先** | ドキュメント正 |
| `0x8B9500` | 同上 | `0x8B950A` が `call 0x889470` → ドキュメントの値は**呼出側のアドレス**（=0x8B9500 起点の文脈） | ドキュメント正 |
| `0x8B97A0` | 同上 | `0x88B3D4` に **`push 0x8b97a0`** が実在 | ドキュメント正 |
| `0x9ED790` | 同上 | 該当バイト列に `0xB37B88` が埋め込まれ、文脈と一致 | ドキュメント正 |
| `0x4AE990` | 同上 | `mov edx,[ecx]` → `mov eax,[edx+0x354]` → `call eax`。文書の「vt+0x354」と**完全一致** | ドキュメント正 |

### 3.2 シンコール・シンボリック定数（7件）

`0x9FAF40`, `0x9FB000`, `0x9FB060`, `0x9FB0C0`, `0x9FB120`, `0x9FB180`, `0x9FB1E0`

いずれも**直近に int3 のない開始点**（= `is_funcstart(a+0x400)` が成立する側）
だが、実バイトを読むとそれぞれ `push 0xb13200` などの**シンボリック定数を積む
シンコール群**で、文書記載のアドレスとバイト列が一致。
直接 E8 呼出が 0 件であることは「関数が存在しない」証拠にはならない。

### 3.3 MGEF クラステーブル（2件）— `0x693FE0` (INVI) / `0x6A6890` (SUDG)

`tmp\re\s91_magic_m3_mgef_dispatch.md` のクラス表 21 エントリを全件計測:

| 信号 | 21件すべて |
|------|-----------|
| 直接 E8 呼出 | **0** |
| `.rdata`/`.data` imm32 参照 | **0** |
| `.text` 内 imm32 参照 | **1** |
| 先頭命令 | **`push -1`**（MSVC SEH プロローグ `push -1; push handler; mov eax,fs:[0]`） |

→ INVI / SUDG は兄弟19件と**完全に同一シグネチャ**。孤立した異常ではない。

**INVI (`0x693FE0`) の直接証拠**:

```
bytes@0x693FDC : 5e 59 c3 cc      ← 直前の関数の末尾 `pop esi; pop ecx; ret` + int3 パディング
bytes@0x693FE0 : 6a ff 68 eb 62 9d 00 64 a1 00 00 00 00 50 51 56
                 push -1 / push 0x9d62eb / mov eax, fs:[0] / push eax  ...
.text imm32 参照 @ 0x9FEC10 : `push 0x693fe0`
```

- `ret` + int3 が**直前に存在**し、その直後が `0x693FE0` → 実在の関数境界
- 直前の int3 が **1バイトのみ**のため `cc×4` 判定は偽陰性だった（判定規則の粗さ）
- コードから `push 0x693fe0` で**明示的に参照**されている

→ **`0x693FE0` は正当な関数。ドキュメント正。**

### 3.4 文脈・範囲表現の誤読（3件）

| 候補 | 見た目 | 実態 | 判定 |
|------|--------|------|------|
| `0x4AE900` | mid-code（`or eax,[edx]`） | 兄弟行が `0x4AE8C0` **先頭確定**（`cc` 前置、`sub esp,0x10; push esi; push edi`）。`0x4AE900` はその**関数内ダンプ開始位置**（=+0x40） | ドキュメント正 |
| `0x695000` | mid-code | 「効果クラスの ctor は `0x68C000`-`0x695000` に集中」という**範囲端**。範囲境界は関数先頭である必要なし | ドキュメント正 |
| `0x697280` | `enter`（デコード不正） | 文書は「Actor attack handler **(0x697280 area)**」＝**概略位置**と明記。`0x69BA90` の呼出元は `0x69730A`（**+0x8A**）で、まさにその area 内。セクション自体も `[部分確定]` | ドキュメント正 |

## 4. 方法論上の教訓（次回以降の規則）

1. **参照数では mid-function 呼出点を判定できない** — 「その位置の実命令が本当に
   その値をオペランドに持つか」を読まないと断定できない（17件中 13件がこれで誤検出）。
2. **`cc×4` 前置は過厳** — int3 パディングが 1〜3 バイトの関数境界を落とす
   （INVI のケース）。`ret + 0..3×int3 + 次先頭` まで広げるべき。
3. **`e8(a)==0` は無意味** — 仮想関数・シンコール・スタブは呼出0が正常。
4. **セクション分割が有効** — `.rdata`/`.data` 参照は決定的、`.text` 内 imm32 は雑音。
5. **範囲表現・"area" 表現・ダンプ位置**を関数先頭として扱わない。
