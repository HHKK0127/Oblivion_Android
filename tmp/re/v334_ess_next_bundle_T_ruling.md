## 3. 最優先: item1 trailer先頭6B

### 3.1 観測事実

- v320 §4-2の実測区間は次のとおり。
  - change record列: `[150,364, 822,976)`、5,527件、崩れ0。
  - trailer候補: `822,976..822,982`、6B = `02 00 00 00 00 00`。
  - index: `@822,982` の `u32=3,437`、続く3,437×u32がfooter開始`836,734`まで完全fit。
- v328 §2-3では、保存側の呼出列が次のように記録されている。
  - `0x465717 -> call 0x45E220`: `+0x74`配列と`+0x78`配列を出力するindex writer。
  - `0x46571A -> call 0x45FB50`: `[0xB3BD00] -> 679480 count -> u32書出＋buffer` のwriter候補。
  - `0x45E220`のfitは`@822,978`からのみ成立し、先頭countは0、次のcountは3,437。
- よって、位置関係だけは次の形が最も強い。

```text
@822,976  02 00 00 00       = 45FB50側のu32 count候補
@822,980  00 00             = 45FB50側buffer/空payload/境界パディング候補
@822,982  6d 0d 00 00       = u32 3437。45E220側の第2配列count
                               （45E220側の第1countは@822,978のu32 0）
```

> 注意: 上のレイアウト図は、既存成果物に記録されたwriter呼出順とfit結果を併記するためのもの。`45FB50`の内部でcount後に何バイトをbufferとして書くかを今回直接再ダンプしていないため、`@822,980`の2Bを確定命名しない。

### 3.2 判定

- `[部分確定]` `@822,976`の`u32=2`が45FB50呼出に対応するcountである可能性は、呼出列・位置・値の一致で強く支持される。
- `[未確定]` 残る2Bが「空bufferの長さ/内容」「writer固有の2B要素」「境界上の別writerの先頭」のいずれかは、45FB50のread/write契約を全文で再確認しないと決着しない。
- `[確定負]` trailer全体を`45E220`の先頭から読む解釈は、v328_17のfit走査で否定される。`45E220`のfit開始は`@822,978`に限定される。
- したがって、旧v320の候補B「`[u16 nTables=2][u32 0]`」を正式採用することはできない。`u32 count=2`を含むwriter境界の方が現証拠に整合するが、2Bの帰属は保留する。

### 3.3 決着に必要な証拠

1. `45FB50`の関数全文で、count書出し後のbuffer長・要素幅・終端を確認する。
2. `679480/679630`のcount/buffer契約を、既存の帯域制約内で再確認する。
3. save#2または別セル数の実検体で、`45FB50`領域のcountが変化するか確認する。

## 4. 残り9件の照合

### item2 — dir[1]=5,527の二重解釈

- `[確定]` writer側は`0x4622D2`で`[0xB333A0]+0x74`配列の`+0xC`を出力。v320実測値は5,527でchange record数と一致。
- `[確定]` reader側`0x462B20`は同じu32をmod byte3再マップ→GetFormへ流す。
- `[未確定]` 同値が「countをformIDとして使う」のか、両者が別表の偶然の同値なのかは、save#2/複数セル検体なしでは決められない。
- 判定は `[部分確定]`。旧v328の残件を維持する。

### item3 — P6の実効果

- `[確定]` `0x464B7F`で`[this+0xA4]==0`のときだけ`GetSystemTime`を呼び、`+0x94`へ書く。
- `[確定]` `GetLocalTime`側は保存ごとの書出経路として別に存在する。
- `[未確定]` 2回目保存で`+0x94`が更新されない（frozen）かは、save#2の実測がないため未決。

### item4 — P8/P9のセクションと`[0xB333A0]`

- `[確定]` 95件表の終端`148,555`、212件表の終端`150,364`、change列の開始が連続する。
- `[確定]` `45E220`の第2配列はログ文字列`WorldSpace ID Array`と対応し、実データの3,437件にfitする。
- `[部分確定]` `441000/4410D0`等を含む呼出列は確定しているが、表①/②の正式なGLOB/GMST分類、および`[0xB333A0]`の正式な全体身元は未決。

### item5 — dir[0]供給元

- `[確定]` `0x462290`で`[[0xB33A98]+0x8C0]`をdir[0]として書く。実値は822,982で、index開始位置と一致する。

- `[未確定]` `+0x8C0`へ822,982相当を作る上流（45F0F0生成リスト等）の因果は未追跡。

### item6 — Δの7×u32要素名とPlayer特殊枠

- `[部分確定]` 7×u32の先頭側が位置(x,y,z)を含むことは命令列・変換・照合から支持される。
- `[未確定]` 残り4要素の正式名と、P1で現れる`0xFEFFFFFF` Player特殊枠の意味は未決。

### item7 — pass2 tail==0分岐

- `[確定]` `0x461BCC`付近に探索失敗時の`[ebx+0x14]=0`経路がある。
- `[未確定]` その後にentryが削除・無効化・別経路再発行されるか、最終ファイルに何が残るかは、該当entryを持つ動的サンプルがないため未決。

### item8 — thumb RGB/BGR

- `[確定]` v320実測はthumb size `8+256×192×3=147,464`、幅256、高さ192、24bpp相当。
- `[未確定]` RGB/BGRの順序は、保存側の`×3B`コピーとD3Dサーフェス形式だけからは決められない。
- 実機CON表示との色比較、または帯域制約を満たすD3D format ctor解析が必要。

### item9 — P5 size返却dst

- `[確定]` v328_19は`E0`基準で、size readのdst=`E0+0x14`、`0x45DE08`の返却参照（`[esp+0x10]`、return時esp=`E0+4`）も`E0+0x14`となることを独立追跡している。
- よって「readファンクタのcleanup規約次第でdst/gotが未分離」という旧残件は解消済み。`FUN_004302B0`の全意味を未解析でも、dstスロット同一性は確定できる。
- `[確定負]` 「sizeが返却されない」というv307旧記載は成立しない。

### item10 — Δ=0x1Cのload側直接対応

- `[確定]` pass2 writer側では28Bブロックがcreated位置/余剰として扱われ、再発行時に除去される。
- `[確定負]` 本検体ではbit31立ちが0件で、44B経路の実例は存在しない。
- `[未確定]` 28Bのload側直接対応が36B読取帯に包含されるか、created flags/type組合せで別経路になるかは、本検体から決められない。
