## 2. 16件の洗い出し方法

1. **V40 のリストを実読み**: `tmp\re\v40_shader_level.md` §4.3 末尾に「レジスタ閾値比較（16件）」が明示されていた（0x406B0B(edi) … 0x80D7D4(edi) の16 VA）。§7-2 で「閾値は直前24byte に即値がなく解決不能」と記載。
2. **実命令 VA の補正**: V40 の VA は生スキャンのバイト列 `48 2F B4 00`（disp32）位置。capstone 再デコードで実 cmp 命令 VA を確定（`cmp dword [0xb42f48], reg` = `39 /r + disp32` のため V40 VA − 2 が命令開始。ただし 0x5102FB のみ V40 VA が命令開始と一致）。
3. **capstone で各サイト前後 10〜40 命令をデコード**し、(a) 命令形式（`cmp [0xb42f48], reg` + jl/setl/je）、(b) 閾値レジスタのロード位置を特定。V40 が「直前24byte」で断念したが、実際は **10〜59 命令前**の `mov reg, imm` / `xor reg,reg` に遡れば全件解決した。
4. **Ghidra デコンパイルで裏付け**: `DAT_00b42f48` を含む 137 行を全走査し、該当関数の行と照合。デコンパイルは `mov reg,2; cmp [mem],reg` を**定数伝播**して `DAT_00b42f48 < 2` / `== 0` の形に簡約済み（アドレスコメント無しのため関数定義行 `void FUN_xxx` から所属を追跡）。
   - 裏付け行: #1→L5139(FUN_00406950)、#2→L8240(FUN_004073d0)、#6→L668975(FUN_007b2aa0)、#8→L681204(FUN_007c3c50)。
   - 残り12件（#3-5, #7, #9-16）の所属関数（FUN_0050ff70 / FUN_007c3240 / FUN_007e7f70 / FUN_007e8e10 / FUN_0080b7a0 / FUN_0080d110）は**未デコンパイル**（DAT_00b42f48 行なし）で、バイナリデコードが一次証拠。

### 3.1 由来分布まとめ

| 閾値 | 件数 | 由来 | ユニークロード |
|---|---|---|---|
| **2** | **14** | `mov reg, imm32(2)` 即値ロード | 8箇所（0x406AB8 / 0x40CC2E / 0x510255 / 0x7C3290 / 0x7E8372 / 0x7E9199 / 0x80B7C9 / 0x80D788）を14箇所の cmp が共有 |
| **0** | **2** | `xor reg,reg` ゼロロード | 2箇所（0x7B2AE2 / 0x7C3C92、いずれも cmp 直前） |
| 引数/スタック/他レジスタ | **0** | — | — |

- V40 が「解決不能（スタック引数/遠距離ロード）」と推測した 2 類型は**実在せず**、全件が即値/xor ロードで解決。
- V40 の「直前24byte」探索では、#1(13命令前=24byte超)・#2(59命令前)・#3/#4/#5(33命令前)・#9/#10(39命令前)・#11/#12(9命令前だが call 域) が取りこぼされた。

### 3.2 V40 カテゴリへの割当内訳

- **≤1系（DAT < 2 / level<=1）**: 12件（#1,2,5,7,9,10,11,12,13,14,15,16）
- **定数選択習語（((DAT<2)-1 & MASK)+base）**: 2件（#3,4 — いずれも `(level<2)?0x0F:0x2F` の flags 構築）
- **==0系（DAT == 0）**: 2件（#6,8）
- 新カテゴリ（呼び出し元依存）: **0件**

> **重要な訂正**: V40 §7-2 は「16件が V40 の定数ベース分類から漏れた」と記載したが、**デコンパイル分類では漏れていない**。デコンパイルは定数伝播済みで、16件は既に「≤1系26 / 習語13 / ==0系6」の内側に数えられていた（§137行照合で確認）。漏れたのは「生スキャンの `cmp [mem], reg` 形式として閾値を特定する段階」のみ。よって V40 ヒストグラム（137件）の件数は変更不要。

## 4. 不明件と理由

**0件 / 16件すべて確定**。

残存の留意点（不明ではないが証拠レベルの差）:
- #2 の所属関数名 `FUN_004073d0` は Ghidra デコンパイルの境界（L5436 起点）由来。実バイナリで 0x4073d0〜0x40CD73 が1関数かは Ghidra 推定に依存するが、比較文（L8240 `DAT_00b42f48 < 2`）と命令列は完全一致。

## 5. V40 の移植3案（a固定 / b GLES caps / c 廃止）への追加影響

前提（V40 §6）: (a) 分岐死 117/137、(b) level2 端末で92件死・level7 端末で91件死、(c) 264参照全消去。今回の16件はデコンパイル分類では既にこれらのカウントに**内包**されていた。

| 案 | 追加影響 | 説明 |
|---|---|---|
| **(a) level=2 固定** | **±0件（内包）** | 14件の `level<2` は常に false（死に分岐）、2件の `level==0` も常に false。V40 の「比較100件全部定数化」に含まれていた。ただしバイナリ書き換え（手作業）対象としては「レジスタ経由で定数化の手順が別」である点が実装上の差（`cmp [b42f48],reg` は `cmp [b42f48],2` 等への2バイト置換で済む） |
| **(b) GLES caps から level 算出** | **±0件（内包）** | GLES 機能で level 2..6 のみを出力する設計（V40 の想定）なら16件全件が両端末とも死に分岐。**新情報**: もし GLES caps 設計で level 0/1 を出す方針を採る場合、≤1系12件（+#3,4 習語の片側、+#6,8 ==0系の片側）＝**最大16件が新たに生存**する。これは V40 の「2値間で分岐する比較約8〜9件」に**追加で+16件**しうる（level 0/1 を出す場合のみ） |
