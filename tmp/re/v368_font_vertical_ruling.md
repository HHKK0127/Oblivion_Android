## §2 ファイル形式とレコード（実データ5種＋EXE 一致）

### 2.1 構造 [確定(実データ＋EXE)]
- **全5種とも14632 bytes = 0x3928** — **EXE の `push 0x3928; call new`（parser 0x5744E0）と完全一致** → **EXE はファイル全体を1バッダに read-all（`file→vfunc+0x1C`=size → `0x42C8E0(file, buf, size)`）[確定(命令)]**。
- **ヘッダ**: `+0x000` = **size float（28.0/35.0/55.0/57.0/22.0 = Kingthings_Regular/Shadowed/Daedric/Handwritten/Tahoma_Bold_Small の5種で一意一致）[確定(実データ)]**／`+0x004`=`1`/`+0x008`=`1`（int）／`+0x00C` = **テクスチャ名文字列（例 'Kingthings_Regular_0_Lod_A'）[確定]**（→ **外部 DDS/テクスチャ参照 [推定高]**）／以降0パディング。
- **レコード領域 = byte0x158 (344) .. 0x3920 に 255 × 56B [確定(実データ)]**（`0x3920−0x158 = 0x37C8 = 255×56` 精密一致。端8バイトは0）— **port の「76Bヘッダ＋344 オフセット・56B歩幅・255 レコード」を実データで裏付け**。
- **EXE のグリフアドレシング**: `movzx eax,al; lea edx,[eax*8]; sub edx,eax; lea eax,[[fontObj+0x38] + edx*8 + 0x128]` = **`base + code×56 + 0x128`**（0x576CDF/0x576961/0x575A91 の3箇所で同一）[確定(命令)]。**base(=raw) とデータ配置 0x158+(code−1)×56 が 0x30/0x28 単位で不一致 → パーサが `[fontObj+0x38]` を再設定（記録再配置）する可能性 [未確定 V-368-1]**（パーサは buffer+0x12C..0x15C/+0x84C../+0x1C6C.. へ in-place 書き込みを行っている＝変換を実行 [確定(命令)]）。

### 2.3 ヘッダ/パーサ側のフォントレベル値 [確定(命令)]
- parser `0x5744E0`: CreateFile(`0x431130(path,0,0x2800,0x80)`) → `[fontObj+0x38]=new(0x3928)` → read-all → `fldz → [fontObj+0x2C]=0, [+0x30]=0` 初期化 → **`lea ecx,[buf+0x150]` を基点に `{buf+0x150, +0x15C, +0x188, +0x1C0, +0x1F8}` の5値を走査して `[fontObj+0x2C]`/`[+0x30]` へ min/max 系の更新（fcomip+cmov アイディオム）[確定(命令)]** — **＝レコード先頭域サンプルから算出される font レベル2値（高さ系 min/max＝ascent/descent 候補 [推定]）**。
- **`+0x000 size` が縦計算に参加**: layout 内 `fild(line_int) + [buf+0](=size28.0) − … → fstp [esp+0x38]`（0x5768C4..0x5768D3）[確定(命令)]（ただし同一スタックスロットに色定数も載る再利用があるため**演算の正確な順序/符号は [未確定 V-368-3]**）。

## §3 縦配置規則（②）の裁定 — **[部分確定]**

1. **レコード由来の垂直メトリクスは存在しない [確定]**（f2/f13=0・他は UV/幅高のみ）→ **port の前提「レコードからベースラインを導けない」は正しい**。
2. **EXE の縦位置は line/font レベル [確定(命令)]**:
   - **line オブジェクト**: `fild dword [lineObj+0x34]`（int フィールド）が Y 系入力に使われる／`[lineObj+0x28]`+`[lineObj+0x2c]` の**整数加算＝ペン累積**（横）。
   - **font レベル**: `fontObj+0x2C`（emit で **X に加算**）と `+0x30`（min/max 結果）。
   - **emit `0x573F10`（3 callers: layout 0x576972/0x576CEE・load時 0x575A9B）**: `pos[0] += f11`（横=advance）＋ **頂点成分に `arg4[2] + f13(=0)` と（別頂点で）`− f10(=v1)` を使用** — **f10=v1（下端UV）の減算は Y反転/基線補正の可能性 [推定]・正確な意味は [未確定 V-368-4]**。
   - **頂点は24B stride（`idx×24`）・法線 (0,0,1) をグローバル `0xB3A6C0/C4/C8`（one-shot init, C8=[0xA30634]）から4角へ複写 [確定(命令)]** — **色定数 (33,59,117)/255=(0.1294,0.2314,0.4588) と 1.0 が layout 初期化 [確定(実測)]**。
3. **下降字の扱い [推定高]**: 原本は **各行（line）の Y 基点＋ヘッダ size でグリフを「行に対して」配置**するため、**ink box の底をベースラインに固定しない** → **下降字 g/p/y は行内で本来の位置に残る**。port の `baseline_rel = min(inkbottom, capBaseline)` は**原本にない独自規約**が `be9in`/`APPearance` 現象の原因 [推定]（原本側の正確な式は V-368-3/4）。

## §4 アトラス形式（③）— **[確定]**
- **実データ: 各グリフが tight UV（アトラス内 tight box）・512×512 [確定(計算)]**（f11/f12 = UVspan×512 が5種全一致）。
- **EXE はレコード UV をそのまま頂点へ書き込む（正規化 UV・追加変換なし）[確定(命令)]** → **均一グリフィネスの証拠なし [確定(否定側)]**。
- **テクスチャは .fnt 外部**（ファイルに画像バイナリなし＝ヘッダ+レコード+8B尾のみ）＋ヘッダ名 `'..._Lod_A'` → **外部 DDS（Lod 命名）[推定高]**、parser 内の `0x70E560`/`0x704800` が画像読込 [推定]。

## §6 残点 **V-368-1..5**
1. **EXE のレコード base（`+0x128`）とデータ配置（`0x158+(code−1)×56`）の不一致**＝パーサの再配置具体内容【中・port の UV 取り出し実装に直結】
2. **f[0]/f[1] の意味**（使用箇所 = 0x57698E 以降のペン更新域が未 decode）【中】
3. **縦計算の正確な演算順/符号**（`y = f(lineInt, size, prevY)` の形は確定・詳細未。`[lineObj+0x34]` の setter も未特定）【高・#96 の縦修正に必須】
4. **emit の `− f10(v1)` の意味**（Y反転か UV 系か）【中】
5. **75.0（double `0xA68950`）の用途**（`fsubr` が layout/load 両方で使用）と外部テクスチャの実ファイル名規則【低】

## §7 検証・自己批評
- probe: **v368_1..v368_9 全 EXIT=0** ＋実データ解析3回（ヘッドダンプ・不変走査・定数読取）。
- **実データ⇔EXE 交叉検証の効果**: `new(0x3928)`＝ファイル実寸、size float 5種一致、f11/f12=UV×512 一致、'!' f1=0 一致 — いずれも片側だけでは出なかった。
