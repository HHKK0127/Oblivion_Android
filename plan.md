**Census correction (2026-09-24)**: an earlier byte-substring scan over the raw ESM reported inflated counts (SCPT 3,046 / QUST 416 / INFO 20,333 / SCDA 9,646 / SCTX 9,992) because a four-character substring match also hits the same tag inside other records' payloads. A record-boundary walk over all 1,167,017 records gives the values above (SCPT 2,393 / QUST 390 / INFO 19,278), independently reproduced by a second reader written from scratch. **Only the SCPT / QUST / INFO counts were actually inflated: both `SCDA 9,646` and `SCTX 9,992` in that list were correct**, as the two corrections below establish. The "SCPT/QUST record counts disagree between tools" risk row is closed by this correction; the reader is byte-complete, not truncated.

**SCDA census correction (2026-09-25)**: the paragraph above is right about SCPT / QUST / INFO but **wrong about SCDA, and its SCDA number is the one that mattered**. A full GRUP-aware record-boundary walk of all 277,504,985 bytes (1,167,016 records, 64 distinct tags, zero remainder) finds **9,646 SCDA subrecords** - the byte-substring scan's SCDA count was accidentally correct while its other counts were inflated. The 2,393 figure counted SCDA only where an SCPT record owns it. The real ownership split is **SCPT 2,393 / INFO 5,552 / QUST 1,701**, i.e. dialogue result scripts and quest stage result scripts carry 7,253 of the 9,646 blocks and **both are far larger than the SCPT corpus that the Phase 67 work has been scoped against**. Reproducing the earlier walk requires three fixes that the first attempt missed: compressed records keep the **20-byte header** (the 4-byte inflate size prefix is counted inside `dataSize`, not added to the header), **zero-size records exist** (e.g. a `STAT` at offset 7,984,486) and must be skipped with `p += 20`, and a GRUP must be **descended into** (`p += 20` and push the end) rather than jumped over. The record count also differs by one (1,167,016 here vs 1,167,017 above).

**SCTX census correction (2026-09-25)**: the 2026-09-24 paragraph called `SCTX 9,992` inflated as well and reported 2,393 instead - the same mistake the SCDA correction above fixes. **9,992 is the correct total.** A GRUP-aware walk that pairs the two subrecords finds **9,992 SCTX against 9,646 SCDA**, and the 346-block difference is fully accounted for: **no block anywhere carries SCDA without SCTX** (all 9,646 have source text), while **346 blocks carry SCTX without SCDA** - QUST 180 of its 2,978 `QSDT` blocks, INFO 166 of its 19,278 records, SCPT 0. Every one of those 346 is a **comment-only or whitespace-only body** (60/60 sampled, QUST totalling 9,190 B and INFO 3,248 B), for example `;Set SEObelisk01EnergyRef.State to 0` (760 B, every line commented out) and `; BLOCKING DIALOGUE to prevent arrest in the Fringe`. The compiler emitted no bytecode because there was nothing to compile, so `SCDA` was omitted rather than written zero-length. **Consequence: executing `SCDA` alone is correct and loses nothing - no SCTX fallback is needed, and a missing `SCDA` means "this block does nothing", not a parse error.** The QUST split over all 2,978 blocks is 1,097 with neither, 180 SCTX-only, 1,701 with both, 0 SCDA-only. INFO carries **at most one `SCDA` and at most one `SCTX` per record** (measured max 1 / 1).

**SCDA reachability audit (2026-09-25)**: the 9,646 SCDA blocks are not merely unhandled, they are **unreachable**. Every entry point into the corpus is either missing or a stub, and the quest stage subsystem that the QUST third depends on is never instantiated.

- **INFO third (5,552 blocks)**: `dialogue_tree.h` declares `uint32_t resultScriptFormID = 0;` but **no assignment to it exists anywhere in the tree** - the only references are the declaration and three `!= 0` guarded reads in `dialogue_runner.cpp` (L89, L186, L243). `dialogue_tree.cpp` L44-69 copies 15 fields from `InfoData` into `DialogueNode` and `resultScriptFormID` is not one of them, and `assets/esm_reader.cpp` does not parse SCDA on the INFO path at all (the SCDA/SCRO walk at L2447-2453 is inside `decodeScript`, i.e. SCPT only). The guard therefore always fails and `executeResultScript()` is dead code.
- **SCPT third (2,393 blocks)**: `ScriptManager::startScript()` has exactly one caller in the tree, `dialogue_runner.cpp` L380, which is inside the dead `executeResultScript()` above. So the 2,393 SCPT blocks are unreachable for the same reason as the INFO blocks.
- **QUST third (1,701 blocks)**: `QuestStageManager::triggerStageScripts()` (`quest_stage_manager.cpp` L364-376) is a stub that logs `ScriptManager integration pending` and returns. It also returns immediately at L365 on `if (!scriptManager_) return;`, and that pointer is never set because **`QuestFlowController` is never instantiated in production code** - a whole-tree grep for `QuestFlowController` / `QuestStageManager` / `QuestObjectiveTracker` finds them only inside `app/src/main/cpp/quest/` plus one comment in `script_functions.cpp` L458. `QuestStageManager` exists solely as a member of `QuestFlowController` (`quest_flow_controller.h` L147), so it is never constructed either, and `QuestFlowController::registerQuest()` / `registerQuests()` have **no callers at all**, so `questRecords_` would be empty even if it were constructed.
- **`SetStage` (`0x1039`, 987 samples, second most common opcode) is a silent no-op**: `script_functions.cpp` L451-463 logs `SetStage(0x%08X, %d)` and returns `success = true` / `returnValue = 1` without changing anything. The adjacent comment states that stage state "is managed by QuestFlowController", which is the subsystem that is never instantiated. `ScriptFunctions::init()` (`script_functions.h` L50-55) takes only `QuestManager* / WorldManager* / NpcManager* / InventoryManager*` and has no parameter through which the stage subsystem could be reached; the wiring call is `renderer.cpp` L1793.
- **The QUST-to-script direction needs no new plumbing**: `QuestStageManager::initialize()` already receives a `ScriptManager*` (`quest_stage_manager.h` L96, member L141) and `QuestFlowController::initialize()` likewise (`quest_flow_controller.h` L91). The missing links are the object itself, the stage data, and the reverse (script-to-stage) pointer.
- **`INDX` is always 2 bytes**: a scan of the top-level `QUST` GRUP in the real ESM finds **2,516 INDX subrecords, every one size 2**, with 136 distinct values in the range 0..255 (most common 10 x245, 20 x223, 100 x214). `QuestRecordParser::parseStageEntry()` (`quest/quest_record.cpp` L321-326) guards on `size < 4` and then reads 4 bytes, so it **always returns false** on real data and would over-read if the guard passed; `parseObjectiveEntry()` (L328-333) has the same shape. No live defect follows today because `QuestRecordParser::parse()` itself has no callers, but any new stage-index reader must treat INDX as u16. The same all-records scan pins every other stage subrecord: **`QSDT` is always 1 byte, `SCHR` is always 20 bytes, `SCRO` is always 4 bytes**, and `SCDA` / `SCTX` are **absent** (not zero-length) when a script is empty - `SCDA` appears 1,701 times with a minimum size of 4.

**QUST stage layout and the `QSDT` run-once flag (2026-09-25, measured over all 390 QUST records)**: the QUST third of the SCDA corpus is **2,978 script blocks spread over 2,516 stages**, not 1,701 blocks in 253 records as the count alone suggests - 1,701 is only the blocks that carry bytecode. A stage is not one script; it is a list of blocks, and **276 stages hold two or more (up to 11)**.

Record order is fixed: `EDID [SCRI] [FULL] [ICON] DATA` followed by the **quest-level `CTDA` run**, then per stage `INDX` followed by 1..N blocks of `QSDT [CTDA*] [CNAM] SCHR [SCDA] [SCTX] [SCRO*]`, then that stage's `QSTA` plus its `CTDA` runs. **TES4 has no `QOBJ` / `NNAM`** - there are no Skyrim-style objectives, so the journal entry is the `CNAM` text and nothing else.

**Every `QSDT` block belongs to a stage, and every `CTDA` has exactly one owner (measured 2026-09-25).** Attributing each subrecord to the stage opened by the most recent `INDX` across all 390 records gives **zero `QSDT` outside a stage**, so the `QSDT` (2,978) minus `INDX` (2,516) surplus of 462 is entirely multi-block stages rather than stray blocks: **2,235 stages carry 1 block, 186 carry 2, 51 carry 3, 14 carry 4, 8 carry 5, 3 carry 6, 11 carry 7, 2 carry 8 and 1 carries 11**, which sums to 2,978 exactly. **5 stages carry an `INDX` and nothing else** (`0x05E2B6` idx 0, `0x05E2B7` idx 10, `0x01DA86` idx 0, `0x025E27` idx 35, `0x027815` idx 2), so a stage entry must be constructible from the index alone with an empty child list - these are also why 16 quests that own stages carry no `QSDT=1` block. Ordering inside a stage is absolute: **no `QSDT` ever appears after that stage's first `QSTA`** (0 of 2,516 stages) and **no stage carries `QSTA` without `QSDT`**, so the stage body is strictly `script entries then target groups`. The prologue order is `EDID [SCRI] [FULL] [ICON] DATA` and not `EDID DATA ...` precisely because of the 719 quest-level conditions, which are the quest's own gating conditions and belong to no stage.

Three consequences. **(1) `CNAM` is per block, not per stage**: of the 194 multi-block stages carrying more than one `CNAM`, **192 have texts that all differ** - SE46 stage 20 pairs `Horkvir Bear-Arm living on the Dementia side of Split is dead.` with the Mania-side wording - so a single per-stage `logText` cannot represent real data. **(2) `SCHR` is 1:1 with `QSDT` while `SCDA` is not**: **1,277 blocks declare a script header but carry neither bytecode nor source** (SE46 stages 20-70 are exactly this shape - flags, conditions and journal text over an empty body), so a block index must be the **`QSDT` ordinal** and never the ordinal of the blocks that happen to have `SCDA`, or the index shifts whenever an empty block is present. **(3) `QSDT` bit 0 is a run-once flag, and the block content confirms it**: **69% of `QSDT=1` blocks contain `StopQuest`** against 2% of `QSDT=0` blocks, **66% of them sit on the quest's final stage and none on a first stage**, they are larger (median `SCDA` 31 B vs 8 B) and far more often conditional (63% carry at least one `CTDA` against 21%). The semantics is therefore: entering a stage fires **every** block of that stage whose conditions pass; a block with `QSDT & 1` is suppressed on all later entries including a return to that stage; a block without it **re-fires on every entry, including after moving back**. A run-once ledger must be keyed `(questFormID, stageIndex, scriptIndex)` **without** `selfRefFormID`, because run-once is a property of the quest stage rather than of the actor that entered it.

**`QSDT` and `DATA` re-measured (2026-09-25, second independent pass over the same 390 records)**: four additions to the table above. **(1) The flag is not merely positional.** Splitting the 1,870 source-bearing blocks by flag *and* by whether the block sits on its record's numerically highest stage shows that `StopQuest` is predicted by the flag far more strongly than by position: `QSDT=1` blocks *below* the highest stage call it **67% (83/123)** against **1% (29/1485)** for `QSDT=0` blocks in the same position, while `QSDT=0` blocks *on* the highest stage call it only **31% (14/45)**. So `QSDT & 1` independently marks the block that **terminates the quest**, not just a block that happens to sit last. **(2) The flag lands on the final stage almost always**: 236 of the 249 flagged quests carry their topmost `QSDT=1` block on their highest stage, 249 of the 378 flagged entries are at the numeric maximum against exactly **1** at the minimum, and 42 sit exactly 100 below it. The only place the two readings diverge is the 13 quests whose highest flagged stage is not their last stage; 8 of those 13 have stages above it that carry `SCDA` but no journal text, i.e. trailing cleanup. **(3) `DATA` is two independent bytes, not a u16 of flags**: byte 0 takes only **7 distinct values** `{0,1,4,5,8,9,13}` (a sparse bitfield over bits 0, 2 and 3) while byte 1 takes **31 values in 0..100** dominated by 60 x140 / 50 x63 / 40 x38 - that is the **quest priority**, so a reader that does `uint16_t flags` folds priority into the flag word. **(4) All 2,338 `CNAM` subrecords are immediately preceded by a `QSDT`**, zero unattributed, which is what makes the per-block attribution in consequence (1) structural rather than conventional. One naming conflict follows: `quest_record.h` L39-43 calls `0x01` `COMPLETE_QUEST` while the paragraph above calls bit 0 a run-once flag, and the measurement says the flag's dominant observable effect is quest termination - WS-B should pick one meaning and must not implement both.

- **`setStage()` has no re-entry guard, and the flag that decides the real rule is now measured**: `quest_stage_manager.cpp` L237-268 fires `onStageTransition()` unconditionally, so a repeated `SetStage` would re-run that stage's scripts. The real rule is **per script block, not per stage** - `QSDT` bit 0 is a run-once flag - so a guard that suppressed *every* repeated entry to a stage, including a genuine move back to an earlier stage, would break the 2,600 repeatable blocks. See the `QUST` stage layout paragraph below.
- **Raw-pointer hazard in the proposed inline path**: `ExecutionContext::init()` (`script_context.cpp` L16-37) stores `script_` and `bytecode_ = script->bytecode.data()` as raw pointers, so an inline `ScriptData` passed by value would dangle once its owner moves or dies, and `ScriptManager::scripts_` is an `unordered_map` whose rehash can already invalidate a live `ExecutionContext` (the existing `startScript()` path passes `&it->second`). The recommended shape is an owning container of `unique_ptr<ScriptData>` on `ScriptManager` plus an index on `ActiveScript`, since `unique_ptr` keeps element addresses stable across vector growth.

Four consequences for the decoder and for the handler order.

**(1) The prologue is SCPT-only.** All 2,393 SCPT blocks start with `0x001D`, and 2,321 of them end with `0x0011` (the other 72 are the prologue alone). **No QUST or INFO block starts with `0x001D`**: QUST first instructions are `0x001C` (671), `0x0015` (365), `0x1037` (155), `0x1039` (130), `0x1058` (68), and INFO first instructions are `0x0015` (3,427), `0x1039` (1,255), `0x001C` (516), `0x1053` (129), `0x0016` (46). **`0x001C` is a reference selector, not a source-line marker** (measured over 4,094 SCPT and QUST blocks, 75,954 instructions, 2026-09-25). The source-line reading was falsified by dumping one record against its SCTX: in `SECindanweScript` the single `0x001C` carries `1` while the `addItem` it precedes sits on source line 10, and both `0x0016` markers carry `1` while their `if` statements sit on lines 5 and 9. What replaced it is more than a byte length: **`0x001C` is `[u16 0x001C][u16 refIndex]` and sets the calling reference of the command that follows to `SCRO[refIndex - 1]`**. In MQ13/MQ14 (corpus record 2504) the seven actors of the `setalert` group (source lines 39-45) carry the values Burd 3, Ulrich 4, Viera 5, Martin 6, Jauffre 7, Baurus 8, Steffan 9, and the `look` group seven lines later (lines 47-53) carries 7, 6, 8, 9, 5, 4, 3 for **the same actors in a different order** - a fixed table read back, which no line number can produce. The whole corpus agrees: of the **1,373 records that contain a `0x001C`**, the largest value never exceeds the number of distinct reference names in the source (**1,373 of 1,373**; median ratio 0.92, p90 1.00), the largest value ever seen inside one record is **16**, and **795 records never exceed 1** - a line number would grow with script length instead. That is also why the marker is followed by **72 distinct opcodes**, most often `0x1021` Enable (983), `0x105E` (799), `0x100D` (632), `0x1022` Disable (618), `0x109E` (612) and `0x1002` AddItem (496): those are the commands that need a calling reference, and the payload-less ones (`Enable`, `Disable`, `Evp`, `StopLook`) can be resolved no other way. **A VM must consume the 4 bytes and assign the calling reference; discarding the value silently breaks every bare `Ref.command`.** The index shares its numbering with the `0x72 <u16>` reference operand, so the two ways of naming a reference agree inside one record: in corpus record 2395 the refs `SE45zBossREF` and `SE45mBossREF` alternate `enable` and `disable` as markers 1 and 2, and the three `SetQuestObject` calls that follow carry `r 01 00`, `r 02 00` and `r 01 00` in their payloads for those same two actors. The value is therefore an index into the record's own reference list and not a list the source rebuilds per statement. One thing is still unsettled: a handful of long records appear to hand one actor two different indices, and the records where that happens are exactly the ones whose SCTX statements run together on merged lines, so the actor-to-statement pairing cannot be read off reliably. A decoder that already holds the record can compare the index against the real reference list directly, so settling this is a five-minute check on the engine side rather than another corpus survey. Byte lengths are unchanged and remain what a length-only decoder needs: `0x0016` / `0x0018` hold `len == payloadLength - 4` in **12,620 of 12,620** cases, `0x0017` is **exactly 2 bytes** in **968 of 968**, and `0x001C` is **exactly 4 bytes** - never the last instruction of a block and never followed directly by another `0x001C`. The leading u16 of `0x0016` spans 1..83 over 83 distinct values and is dominated by `1`; nothing in the corpus shows it selecting a reference, so it may be read and discarded.

**Expression payloads are mixed text and binary.** The `0x0015` / `0x0016` / `0x0018` payloads carry the compiled expression as a stream in which operators and keywords stay ASCII while variables and calls are binary: a variable is `[type char][u16 index]` with `f` / `s` / `r` / `l`, a numeric literal is `n` + `u32`, a call is `X` + `[u16 functionID]` + `[u16 argumentBytes]` + arguments, and operators are **postfix**, so `if IsActionRef player == 1` compiles to ` ` `X1069`(5 B) ` ` `<r1>` ` ==`. Function IDs reuse the standalone opcode numbers - `0x103A` is `GetStage` and `0x1069` is `IsActionRef` - so a condition-only function such as `IsActionRef` never appears as a statement. Two independent disassembles reproduce the source line for line: `if ( GetStage SQ07 >= 10 ) && ( GetStage SQ07 < 100 )` and `set Dark14Honor.paralyze to 1`.

**Statement operands use one framing, `[u16 n][n typed tokens]`**, and **`n` is the argument count, not a token count** (measured 2026-09-25). Over 1,728 statements that pair positionally with exactly one instruction, `len(tokens) == n` in **1,714 (99.19%)**. The 14 exceptions are `0x1002` AddItem (11) and `0x1052` RemoveItem (3), and every one of them is `+1` on a source line that prefixes a calling reference: `Player.AddItem Gold001 FGConversations.FGRewards` carries `n = 2` with tokens `[<r2>][<r3>][<s5>]`. **Quest and dialogue records (measured)**: `QUST` is 390 records and `INFO` is 19,278, and both are now fully accounted for. The top-level walk needs no descent: one `GRUP` labelled `QUST` holds all 390 records directly, and one labelled `DIAL` holds 3,817 `DIAL` records plus 3,053 nested `GRUP`s of type 7 whose 4-byte label is the parent `DIAL` FormID and whose children are the `INFO` records, so `INFO` is never inline in `DIAL`. The linkage that matters for `registerQuests()` is `INFO.QSTI` (4 bytes, present in **19,278 / 19,278** records) naming the owning quest, which resolves to **337** of the 390 quests.

A `QUST` record is `EDID` + optional `SCRI` (4-byte quest-script FormID, 255 / 390) + optional `FULL` (343 / 390) + `DATA` (**2 bytes, 390 / 390**) + optional `ICON` (283 / 390), then zero or more **stage blocks**, each introduced by `INDX` (**u16, size 2 in 2,516 / 2,516**). **125 of the 390 quests carry no `INDX` at all.** Inside a stage block come one or more **script entries**, each introduced by `QSDT` (**u8, size 1 in 2,978 / 2,978**; the value is 0 in 2,600 and 1 in 378 and never anything else, so it is a single flag bit), optionally preceded by `CTDA` (24 bytes, 3,784 in `QUST`) and followed by optional `CNAM` (the journal log line for that stage, 2,338), then `SCHR` (**20 bytes, exactly one per `QSDT`, 2,978**) and then the compiled `SCDA` / `SCTX` / `SCRO` chunks. `QSDT` (2,978) outnumbers `INDX` (2,516) because **462 stage blocks carry a second script entry** (for example `INDX QSDT CTDA CNAM SCHR QSDT CTDA CNAM SCHR` x34), so the correct shape is `QuestStageEntry` keyed by `INDX` with a **child list of script entries**, not the reverse, and `scriptIndex` is the ordinal of the `QSDT` within its stage. `QSTA` (8 bytes, 1,154) is a stage target that owns the `CTDA` records that follow it (1, 2, 3, 4, 5, 6 or 8 of them, and 8 carry none), so a condition must attach to the target that precedes it rather than to the stage.

`QuestRecordParser::parse()` currently contradicts all of this: it reads `INDX` as a **u32 objective index** and pushes a `QuestObjectiveEntry`, it attaches `CNAM` to that objective, it attaches `CTDA` to `stages.back()`, and it builds stages from `QSTN` / `QSTF` / `QSTR`, **none of which occurs in any of the 14,489 `QUST` subrecords**. `parseStageEntry()` also demands `size >= 4` and copies 4 bytes, so it would reject every real `INDX`. The quest subrecord set is exactly `SCRO` 6,119 / `CTDA` 3,784 / `QSDT` 2,978 / `SCHR` 2,978 / `INDX` 2,516 / `CNAM` 2,338 / `SCTX` 1,881 / `SCDA` 1,701 / `QSTA` 1,154 / `EDID` 390 / `DATA` 390 / `FULL` 343 / `ICON` 283 / `SCRI` 255, with no other tag anywhere.
